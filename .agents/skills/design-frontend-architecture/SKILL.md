# Проектирование frontend-архитектуры

Сначала сформировать проверяемый дизайн изменения, затем реализовывать минимальный вертикальный срез. Не создавать абстракции только ради симметрии структуры.

## Собрать контекст

1. Прочитать `package.json`, `src/App.tsx`, затрагиваемые модули и их публичные `index.ts`.
2. Найти ближайшую существующую реализацию аналогичного сценария.
3. Проверить theme, переводы, aliases и правила форматирования.
4. Для задач с данными прочитать [data-and-state.md](references/data-and-state.md).
5. Для изменения каталогов или импортов прочитать [module-boundaries.md](references/module-boundaries.md).

## Сформировать design brief

До кода определить пользовательскую цель, маршрут, источник данных, минимальный контракт, владельца каждого состояния, композицию компонентов, UI-состояния, переводы, риски и способ проверки.

Не скрывать решения, влияющие на API, URL или общую модель данных, внутри компонента.

## Разместить ответственность

- `pages` — route-level композиция экрана;
- `layout` — общий каркас и навигация;
- `components` — предметные составные блоки;
- `ui` — независимые переиспользуемые примитивы;
- `providers` — сквозные контексты и инфраструктура;
- `api` — HTTP-клиенты и endpoints по контракту из `docs/api-contract.md`;
- `queries` — query keys и TanStack Query hooks;
- `validation` — схемы валидации;
- `translation` — пользовательские строки.

## Выбрать владельца состояния

- URL — фильтры, сортировка, пагинация и состояние, которым нужно делиться;
- TanStack Query — удалённые данные и cache;
- React Hook Form — значения и ошибки формы;
- локальный React state — состояние одного взаимодействия;
- Context/provider — стабильное сквозное состояние с удалёнными потребителями.

Не копировать query data в локальный state без необходимости редактируемого черновика.

## Спроектировать вертикальный срез

1. Типы и граница получения данных.
2. Route/page orchestration.
3. Состояния результата.
4. Предметные компоненты.
5. Переводы, тема и адаптивные стили.
6. Проверки критической логики.

Проверить отсутствие циклов и дублирования состояния, малый типизированный публичный API, прямое открытие маршрута, явное поведение ошибок и возможность заменить источник данных без переписывания UI.

После реализации запустить `npm run lint:ci`, `npm test` и `npm run build`.
